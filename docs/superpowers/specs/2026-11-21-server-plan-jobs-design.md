# วางแผนทริปบนเซิร์ฟเวอร์ ปิดแอปแล้วยังทำต่อจนเสร็จ — design

วันที่ 21 พ.ย. 2026 · สถานะ: เจ้าของอนุมัติให้สร้าง ("implement เลย" 21 พ.ย. 2026)

## ทำไม

เจ้าของลองบน iPhone แล้วแผน 8 วันหยุดที่ 2 วัน log ของเซิร์ฟเวอร์บอกว่าแอปเป็นตัวสั่งให้ทำทีละวัน (วันละ 75–93 วินาที) พอการเชื่อมต่อของมือถือหลุดสองรอบติด แอปก็เลิก ทั้งที่เซิร์ฟเวอร์ยังทำงานอยู่ (ดู commit `437393e`)
แก้ฝั่งแอปไปแล้วให้ทำต่อเมื่อกลับมาที่แอป แต่ระหว่างพับแอปแผนก็ยังไม่เดิน เจ้าของเลือกให้ย้ายการวางแผนไปทำบนเซิร์ฟเวอร์ทั้งหมด ปิดแอปแล้วก็ยังทำต่อจนเสร็จ

## เป้าหมาย

1. กดสร้างแผนแล้ว เซิร์ฟเวอร์วางแผนจนครบทุกวันเอง จะเปิดแอป พับแอป หรือปิดแอปก็ได้
2. เปิดแอปเมื่อไหร่ก็เห็นวันที่ทำเสร็จแล้ว และเห็นแผนเต็มเมื่อเสร็จ โดยไม่ต้องกลับไปหน้างานของ AiGo
3. ปุ่ม "หยุดสร้างแผน" และ "ลองใหม่" ยังใช้ได้
4. ใช้ได้ทั้งผู้เยี่ยมชม (ไม่ได้ล็อกอิน) และบัญชี

## ไม่ทำ (รอบนี้)

- แจ้งเตือนบนมือถือเมื่อแผนเสร็จ: ต้องตั้งระบบแจ้งเตือนและใช้บัญชี Apple Developer แบบเสียเงิน ทำทีหลังได้
- ทำให้แต่ละวันเร็วขึ้น (เปลี่ยนรุ่น AI) เป็นเรื่องแยก
- การแก้แผนวันเดียว (R13, `replanDay`) ยังใช้แบบเดิม เพราะเสร็จในครั้งเดียว

## ห้ามเกิด

- งานที่วนไม่จบและเผาค่า AI ไปเรื่อยๆ
- โควตาทริปฟรีถูกนับสองครั้ง หรือไม่ถูกนับเลย
- คนอื่นเปิดดูแผนของเราได้
- วันเดียวกันถูกสร้างซ้ำพร้อมกันจากสองที่

## แนวทางที่พิจารณา

## การออกแบบ

### ฐานข้อมูล

ตารางใหม่ `plan_jobs` (migration ใน `supabase/`):

- `id` uuid, `token` ข้อความสุ่มที่ส่งให้แอป ใช้แทนการล็อกอินตอนถามสถานะ (ผู้เยี่ยมชมไม่มีบัญชี)
- `owner` (`user:<id>` หรือเลขเครื่อง) ใช้นับโควตา
- `request` (คำขอเดิมที่แอปส่งให้ `generate-itinerary` รวมบทสนทนา), `total_days`
- `days` (วันที่เสร็จแล้ว เรียงตามลำดับ), `title`
- `status`: `running` / `done` / `failed` / `stopped`, `error`
- `attempts` (จำนวนรอบติดกันที่ไม่ได้วันใหม่), `lease_until` (หมดเวลาจอง), `created_at`, `updated_at`
- เปิด RLS ไม่มี policy: อ่านและเขียนได้เฉพาะ edge function (service role)

### `generate-itinerary` รับงานแบบใหม่ (ใช้โค้ดสร้างแผนเดิมทั้งหมด)

- `{ job: 'start', ...คำขอเดิม }`: ตรวจข้อมูล ตัวตน และโควตาเหมือนวันนี้ แล้วสร้างแถวงาน ทำรอบแรกต่อเบื้องหลัง (`EdgeRuntime.waitUntil`) และตอบ `{ jobId, token, totalDays }` ทันที
- `{ jobId, token }` (รอบทำงาน ปลุกจากตัวตั้งเวลาหรือจาก start):
  - จองงานเฉพาะเมื่อสถานะยัง `running` และไม่มีใครจองอยู่ ถ้าจองไม่ได้ให้จบเลย
  - ทำต่อจากวันที่ขาด โดยส่งรายการที่วางไปแล้วให้ AI เหมือน `fromDay` และ `planned` ของวันนี้
  - วันไหนเสร็จบันทึกลงแถวทันที พร้อมต่อเวลาจอง ถ้าเจอว่างานถูกหยุดแล้ว ให้เลิกทำ
  - ใกล้หมดเวลาของ worker (กติกาเดิม 125 วินาที) ให้ปล่อยการจองแล้วจบรอบ ครบทุกวันให้เปลี่ยนเป็น `done`
  - รอบที่ไม่ได้วันใหม่ (AI ล้มหรือรอบก่อนถูกตัด) นับ `attempts` ครบ 4 รอบติดกัน หรืองานค้างเกิน 2 ชั่วโมง ให้เปลี่ยนเป็น `failed`
  - ไม่จองงานถ้า worker นี้อายุเกิน 20 วินาทีแล้ว (worker ที่ถูกใช้ซ้ำมีเวลาเหลือน้อย) ปล่อยให้รอบปลุกครั้งหน้าไปได้ worker ใหม่
- `{ job: 'status', jobId, token, have }`: ตอบสถานะและเฉพาะวันที่แอปยังไม่มี (`have` = จำนวนวันที่แอปมีแล้ว)
- `{ job: 'stop' | 'resume', jobId, token }`: หยุดงาน หรือเริ่มต่อจากที่ค้าง (resume ล้าง `attempts`)
- โควตา: นับครั้งเดียวต่องาน เมื่อบันทึกวันแรกได้ (แบบเดียวกับวันนี้ที่นับหลังรอบแรกได้ผล) นับตาม `owner`
- แบบเดิมที่ตอบเป็นสตรีม (SSE) ยังอยู่สำหรับ `replanDay`

### ตัวตั้งเวลา

`pg_cron` ทุก 15 วินาที: หางานที่ `running` ไม่มีคนจอง และขยับล่าสุดไม่เกิน 2 ชั่วโมง แล้วเรียก `generate-itinerary` ด้วย `{ jobId, token }` ผ่าน `pg_net` (ใช้ publishable key แบบเดียวกับแอป) ทั้งสอง extension ติดตั้งในโปรเจกต์แล้ว

### แอป

- หน้างานของ AiGo เรียก `job: 'start'` แทนการวนขอทีละวันในแอป แล้วเก็บ `jobId` กับ `token` ไว้ในทริป (บันทึกในเครื่องและในบัญชีเหมือนข้อมูลทริปอื่น)
- ตัวเก็บทริปถามสถานะงานที่ยังไม่เสร็จทุก 3 วินาทีระหว่างแอปอยู่บนจอ (หน้าไหนก็ได้) แล้วเติมวันใหม่ลงทริป เปิดแอปครั้งหน้าก็ถามต่อจนเสร็จ
- หน้างานแสดงความคืบหน้าแบบเดิม (จุดกระพริบ "กำลังวางวันที่ N จาก M" นาฬิกา) จากข้อมูลงาน ปุ่มหยุดและลองใหม่เรียก API ของงาน
- ข้อความบนหน้าเปลี่ยนเป็น "ปิดแอปได้เลย ฉันวางแผนต่อบนเซิร์ฟเวอร์ เปิดแอปเมื่อไหร่ก็เห็นแผน"
- ลบตัววนขอทีละวันในแอป (`generateItinerary` และกติกา `nextRound` ที่เพิ่งเพิ่ม) เพราะเซิร์ฟเวอร์ทำแทนแล้ว

### ความเร็ว

ไม่เปลี่ยนในรอบนี้: รุ่น AI ปัจจุบันใช้วันละ 75–93 วินาที ทริป 8 วันจึงใช้ราว 12–15 นาที (รวมช่วงรอปลุกระหว่างรอบ) ถ้าเปลี่ยนเป็นรุ่นที่เร็วกว่า ระบบนี้ใช้ต่อได้เลยและจะเร็วขึ้นตาม

## วิธีตรวจ

- สร้างงานทริป 3 วันจากสคริปต์ แล้วไม่ถามสถานะเลย (เหมือนปิดแอป) งานต้องเสร็จเองครบทุกวัน
- จำลองรอบที่ถูกตัด (ตั้งเวลาจองให้หมด) แล้วงานต้องทำต่อได้ ไม่สร้างวันซ้ำ
- กดหยุดกลางทางแล้วไม่มีวันใหม่เพิ่ม และกดลองใหม่แล้วทำต่อ
- โควตาถูกนับครั้งเดียวต่องาน ทั้งผู้เยี่ยมชมและบัญชี
- token ผิดต้องอ่านสถานะไม่ได้
- งานที่ AI ล้มติดกันต้องจบด้วย `failed` ไม่วนไม่จบ

## ที่ผมตัดสินเอง (เจ้าของแก้ได้)

- ใส่ใน `generate-itinerary` ตัวเดิม ไม่แยกฟังก์ชันใหม่ เพราะใช้โค้ดสร้างแผน การตรวจโควตา และ cache เดิมได้ทั้งหมด
- ปลุกทุก 15 วินาทีด้วย `pg_cron` เพราะกู้ตัวเองได้เมื่อรอบไหนถูกตัด
- แอปถามสถานะเป็นระยะ ไม่ใช้ Realtime เพราะผู้เยี่ยมชมไม่มีบัญชีให้ Realtime ตรวจสิทธิ์
- ใช้ token ต่องานแทนการผูกกับบัญชี จึงใช้ได้ทั้งผู้เยี่ยมชมและบัญชีด้วยวิธีเดียว
- ยังไม่มีแจ้งเตือนตอนเสร็จ

## ตัดสินระหว่างสร้าง (จากผู้ตรวจแบบร่าง)

- ไม่ใช้แคชแผนที่ใช้ร่วมกัน (`itinerary_skeleton_cache`) เมื่อคำขอมีบทสนทนา (คำขอจากแอปทุกครั้ง) เพราะ key ของแคชไม่ได้ดูบทสนทนา คนหนึ่งจึงได้แผนที่ปรับตามแชตของอีกคน และแผนของเราไปถึงคนอื่น
- กติกาหยุดก่อนหมดเวลาประมาณเวลาวันถัดไปจากช่วงห่างระหว่างวันที่เสร็จในรอบนั้น (ก่อนมีวันที่สองถือว่า 20 วินาที) งบ 125 วินาทีเท่าเดิม เดิมนับเวลาคิดของวันแรก (25–75 วินาที) เป็นเวลาของทุกวัน รอบจึงหยุดหลังวันเดียว
- ทางสตรีมรับ `fromDay` > 1 เฉพาะการแก้แผนวันเดียว (`replanDay`) เพราะการขอต่อหลายวันแบบเดิมได้วันโดยไม่ใช้โควตา งานบนเซิร์ฟเวอร์ใช้แทนแล้ว
- นับโควตาตอนบันทึกวันแรกของงานได้

## ที่ปล่อยให้ผู้สร้างเลือก

- รูปแบบเก็บ `jobId` ในทริป และตำแหน่งของตัวถามสถานะในแอป
- รายละเอียดการแยกโค้ดส่วนสตรีมกับส่วนงานใน `generate-itinerary`
